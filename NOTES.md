## File architecture (SCRIPT LOAD ORDER MATTERS)
index.html loads scripts in this order, each with a `?v=N` cache-buster:
supabase-js CDN -> main.js -> supabase-auth.js -> supabase-data.js -> supabase-food.js -> supabase-waittimes.js -> leaderboard.js

Later files intentionally OVERRIDE functions from earlier ones (plain function
declarations; the last definition wins). That is how the backend was layered on
without heavily rewriting main.js.

- **index.html** — markup: landing shell + app shell (views: **home** [now includes the profile content — see below], community, food, photos, about) + modals. Bump `?v=` when editing a script/style.
- **styles.css** — all styles.
- **img/** — the project's first raster assets (everything before this was inline SVG/CSS). `coffee-cup.png` (About page donate card background), `logo.png` (the real T/F monogram artwork, replaced the old hand-coded SVG compass mark in both header logo spots), `favicon.png` (the same logo composited onto the rounded navy-square card the old SVG favicon used). Source art lives outside the repo, usually at `C:\Users\SeanDaniel\Pictures\` or `...\Pictures\Turnstiles Images\`; there's no image editor in this environment, so processing (resize, white-background removal, compositing) is done with PowerShell's `System.Drawing`/`Bitmap` via the `LockBits` API. **Two background-removal techniques depending on the art**: flood-fill from the image edges (`coffee-cup.png`) when the art has legitimate white highlights to preserve (e.g. porcelain glare) that a global threshold would incorrectly erase; plain global near-white thresholding (`logo.png`) when it doesn't — flood-fill would've left enclosed white regions (like the disc inside the logo's ring) opaque since they're not connected to the image border.
- **main.js** — demo/core: `STATE` (in-memory cache), toast/overlay/dropdown helpers, `showView` (accepts the legacy `'profile'` name and silently maps it to `'home'`, so old call sites still work), guest-browse, form helpers, renderers (`renderLeaderboard`, `renderCommunity`, `renderProfile`, `updatePassport`, `updateParkCounts`), `foodEmoji`, demo seed. **The Supabase client is created at the END of main.js**: `SUPABASE_URL`, `SUPABASE_KEY` (publishable), `const sb`. **Rank tiers** (`MONTHLY_TIERS`/`YEARLY_TIERS`, `getMonthlyTier`/`getYearlyTier`, `checkinsThisMonth`/`checkinsThisYear`, `tierEmblem`/`tierBadge`) also live here. **`avatarHtml(avatarUrl, emoji, extraClass)`** is the one place that decides emoji-vs-photo — every avatar-rendering call site across every file goes through it, see below.
- **supabase-auth.js** — real auth: `profileToUser`, `fetchProfile`, `enterApp`, `doSignIn`, `regSubmit`, `regNext`, `doSignOut`, `restoreSession` (stays logged in across refresh). **Login is by EMAIL**, not username.
- **supabase-data.js** — `loadData()` reads tables into STATE + rerenders; `rerenderActive`; `downscale`/`uploadPhoto` (Storage upload); overrides `enterApp`/`guestBrowse`; real `submitCheckin`/`submitFoodReview`/`submitPhoto`; `deleteCheckin`; `openUserProfile(userId)` (read-only view of another passholder — redirects to your own editable profile if `userId` is you). Clears the demo seed.
- **supabase-food.js** — overrides `loadData` (adds `spot`, `photo_url`, `food_favorites`, `wait_times`); food search-and-pick; `submitFoodReview` (new + EDIT via `frEditId` + photo, auto-clears a matching "want to try" favorite on new submit); `getFoodAggregates`/`renderFood` grouped by name+park+spot (click a row -> `openFoodDetail` modal with per-review score/comment/photo + `openUserProfile` link); `renderMyFoodReviews` + `editFoodReview`/`deleteFoodReview` and `renderFoodFavorites` + `rateFavorite`/`removeFavorite`/`toggleFavoriteCurrent` ("Want to Try" list, both on profile); wraps `renderProfile`. **This is the file that owns `loadData()` now — if you add another table, extend the fetch here rather than overriding `loadData` yet again in a new file** (see `supabase-waittimes.js`, which deliberately does NOT re-override `loadData`).
- **supabase-waittimes.js** — `RIDES_BY_PARK` (curated per-park attraction rosters, park names must match the ones used elsewhere); `updateRideOptions` (Park -> Ride cascading select); `submitWaitTime`/`deleteWaitTime`; `renderWaitTimes` dispatches to `renderWaitTimesToday` (today's individual submissions, no averaging - live feed) and `renderWaitTimesYesterday` (per-ride average posted/actual wait, computed from yesterday's rows only); `switchWaitTimesTab`. "Today"/"yesterday" are just a filter on `created_at` against the viewer's local calendar day (`isSameLocalDay`) - nothing is ever archived or deleted, so a longer history is just a filter change away later.
- **leaderboard.js** — `buildLeaderboard` override + `LB_GROUPS` (Disney/Universal); `selectResort`/`selectLbPark`; two-level filter (resort -> park). Water parks folded in: Blizzard Beach + Typhoon Lagoon -> Disney; Volcano Bay -> Universal.

## Supabase
- Tables: `profiles` (has `avatar_url`), `checkins`, `food_reviews` (has `spot`, `photo_url`), `photos`, `food_favorites`, `wait_times`. See `supabase/schema.sql`.
- Trigger `on_auth_user_created` auto-creates a profile from signup metadata.
- RLS: public read on everything **except `food_favorites`, which is private (own rows only)** — it's a personal reminder list, not social content; write/update/delete only your own rows everywhere.
- The publishable key in main.js is SAFE (public by design; RLS protects data). NEVER commit the service_role key or DB password.
- Email confirmation is currently OFF (for testing). Before launch: turn it ON and set Supabase Auth -> URL Configuration -> Site URL to the Vercel domain.

## Conventions / gotchas
- After editing any .js/.css, bump its `?v=N` in index.html or the browser serves stale.
- Photos: new uploads are downscaled client-side then pushed to the `photos` Storage bucket via `uploadPhoto()`; `photos.image_url` stores the public Storage URL. Older rows created before this change still have base64 data URLs in `image_url` — both render identically via `<img src>`, no backfill needed.
- STATE is a client cache; call `loadData()` after any write to refresh + rerender.
- Multi-line edits to index.html/*.js were done via a small Python script (io.open read/replace/write) run through Bash — reliable for multi-line HTML.
