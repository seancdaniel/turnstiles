## File architecture (SCRIPT LOAD ORDER MATTERS)
index.html loads scripts in this order, each with a `?v=N` cache-buster:
supabase-js CDN -> main.js -> restaurants-data.js -> supabase-auth.js -> supabase-data.js -> supabase-food.js -> supabase-festivals.js -> supabase-waittimes.js -> waittimes-live.js -> supabase-donors.js -> supabase-invite.js -> leaderboard.js

Later files intentionally OVERRIDE functions from earlier ones (plain function
declarations; the last definition wins). That is how the backend was layered on
without heavily rewriting main.js.

- **index.html** — markup: landing shell + app shell (views: **home** [the user's own profile: the `.cred` passholder-credential hero + the `.passport` ticket, see below], community, food, festivals, photos, waittimes, thanks, about) + modals. Bump `?v=` when editing a script/style.
- **styles.css** — all styles.
- **img/** — the project's first raster assets (everything before this was inline SVG/CSS). `margarita.png` (About page donate card background), `logo.png` (the real T/F monogram artwork, replaced the old hand-coded SVG compass mark in both header logo spots), `favicon.png` (the same logo composited onto the rounded navy-square card the old SVG favicon used). Source art lives outside the repo, usually at `C:\Users\SeanDaniel\Pictures\` or `...\Pictures\Turnstiles Images\`; there's no image editor in this environment, so processing (resize, background removal, compositing) is done with PowerShell's `System.Drawing`/`Bitmap` via the `LockBits` API. **Check for existing transparency before processing** (`Bitmap.GetPixel` on a corner, look at `.A`) — `margarita.png` arrived already background-removed and only needed a resize. When an image genuinely needs background removal, pick the technique by whether the art has legitimate white highlights to preserve: flood-fill from the image edges (leaves enclosed white regions like a disc inside a ring untouched, so only use it when that's what you want) vs. plain global near-white thresholding (simpler, but wrong for art with real white highlights like porcelain glare — used for `logo.png`, previously for the now-removed `coffee-cup.png`).
- **main.js** — demo/core: `STATE` (in-memory cache), toast/overlay/dropdown helpers, `showView` (accepts the legacy `'profile'` name and silently maps it to `'home'`, so old call sites still work), guest-browse, form helpers, renderers (`renderLeaderboard`, `renderCommunity`, `renderProfile`, `updatePassport`, `updateParkCounts`), `foodEmoji`, demo seed. **The Supabase client is created at the END of main.js**: `SUPABASE_URL`, `SUPABASE_KEY` (publishable), `const sb`. **Rank tiers** (`MONTHLY_TIERS`/`YEARLY_TIERS`, `getMonthlyTier`/`getYearlyTier`, `checkinsThisMonth`/`checkinsThisYear`, `tierEmblem`/`tierBadge`/`credPlateHtml`) also live here. **`avatarHtml(avatarUrl, emoji, extraClass)`** is the one place that decides emoji-vs-photo — every avatar-rendering call site across every file goes through it, see below.
- **supabase-auth.js** — real auth: `profileToUser`, `fetchProfile`, `enterApp`, `doSignIn`, `regSubmit`, `regNext`, `doSignOut`, `restoreSession` (stays logged in across refresh). **Login is by EMAIL**, not username.
- **supabase-data.js** — `loadData()` reads tables into STATE + rerenders; `rerenderActive`; `downscale`/`uploadPhoto` (Storage upload); overrides `enterApp`/`guestBrowse`; real `submitCheckin`/`submitFoodReview`/`submitPhoto`; `deleteCheckin`; `openUserProfile(userId)` (read-only view of another passholder — redirects to your own editable profile if `userId` is you). Clears the demo seed.
- **supabase-food.js** — overrides `loadData` (adds `spot`, `photo_url`, `food_favorites`, `wait_times`, `donors`, `festivals`/`festival_reviews`/`festival_favorites`); food search-and-pick; `updateRestaurantOptions`/`handleSpotSelect`/`setSpotValue`/`getSpotValue` (Park -> Restaurant cascading select for the "Where" field, backed by `RESTAURANTS_BY_PARK` in `restaurants-data.js` - see that file's own entry below); `submitFoodReview` (new + EDIT via `frEditId` + photo, auto-clears a matching "want to try" favorite on new submit); `getFoodAggregates`/`renderFood` grouped by name+park+spot (click a row -> `openFoodDetail` modal with per-review score/comment/photo + `openUserProfile` link); `renderMyFoodReviews` + `editFoodReview`/`deleteFoodReview` and `renderFoodFavorites` + `rateFavorite`/`removeFavorite`/`toggleFavoriteCurrent` ("Want to Try" list, both on profile); wraps `renderProfile`. **This is the file that owns `loadData()` now — if you add another table, extend the fetch here rather than overriding `loadData` yet again in a new file** (see `supabase-waittimes.js`/`supabase-festivals.js`, which deliberately do NOT re-override `loadData`).
- **supabase-festivals.js** — EPCOT Festivals, a separate space for festival-specific food reviews (Food & Wine, Flower & Garden, Festival of the Arts, Holidays, etc.) reachable via a hover/tap submenu off the "Food Scores" nav item (`.nav-has-sub`/`toggleNavSub`/`closeNavSub` in `main.js`+`styles.css` - CSS `:hover` on desktop, JS click-toggle fallback for touch, plus flat extra links in both mobile hamburger menus), so seasonal content never mixes into the year-round Food Scores page. **Reviews are about the food item, not the booth** — same shape as regular food reviews (`item_name` = what you're rating, `booth_name` = where you got it, optional) rather than the booth being the thing rated; got this backwards on the first pass (had it as "rate a booth", food review as an afterthought) and corrected it, including a schema migration since the tables were already live. "Current" festival is just `STATE.festivals[0]` (newest `created_at`, per the `order()` on that query in `supabase-food.js`'s `loadData`) - everything older is automatically the archive, no active/inactive flag to keep in sync. Form (`overlay-festival-review`): food item name (plain text with a `<datalist>` autocomplete off existing item names for the current festival - lighter than Food Scores' full search-and-pick UI, intentional given how much simpler this feature needs to be) + booth (optional, same idea, its own datalist), score, review, optional photo (dual-written to `photos` with `park:'EPCOT'`, same as food reviews, so festival shots also show up in Community Photos). `getFestivalAggregates(festivalId)`/`renderFestivalLists()` group by item name + booth (case-insensitive) and are reused for both the Current tab and whichever archived festival is being viewed; `renderFestivalView()` is the `showView('festivals')`/`rerenderActive()` entry point. Archive tab (`switchFestivalTab`) lists past festivals with a review count each; clicking one (`openFestivalArchive`/`closeFestivalArchiveDetail`) drills into that festival's own Top Rated/Most Reviewed lists read-only via the same renderer. `openFestivalDetail` (food detail modal, every individual review) hides the "Want to Try" button entirely when viewing an archived festival's item - favoriting only makes sense for the festival that's actually happening. "My Festival Reviews"/"Want to Try (This Festival)" (`renderMyFestivalReviews`/`renderFestivalFavorites`, current-festival-scoped only) live on the Festivals page itself, deliberately **not** folded into the merged home/profile page, per the same "don't clog it up" reasoning that keeps this whole feature off Food Scores. Starting a new festival is a one-line manual SQL insert (see `supabase/schema.sql`) - infrequent enough that a whole admin UI wasn't worth building, same call made for `donors`.
- **restaurants-data.js** — `RESTAURANTS_BY_PARK`: curated dining locations for all 31 park/resort options in the food review form's "Park or Resort" select (the 10 parks/water parks, **Disney Springs**, and the 20 Disney resort hotels - resort restaurants count too, people eat at 'Ohana and Boma). Same pattern as `RIDES_BY_PARK` in `supabase-waittimes.js`: a plain hardcoded list, no database table, loaded early (right after `main.js`) so `supabase-food.js` can read it. Each entry is `[name, type]` with `type` one of `'table'` / `'quick'` / `'snack'` (named walk-up spots only, deliberately excludes generic unnamed carts like "Popcorn Cart" - user's call when asked). Curated from general knowledge, not scraped from Disney/Universal's own live dining pages, so it **will** drift as restaurants open/close/rename - Epic Universe's section is the least certain since it's the newest park, and **Disney Springs is its own drift risk since that lineup rotates more than an actual theme park's does**. If a user reports something missing, closed, or misnamed, that's real: edit the array for that park and bump both `restaurants-data.js` and `supabase-food.js`'s `?v=` in `index.html`. Selecting "Other / not listed here..." reveals a plain text fallback (`#fr-spot-other`) rather than hard-blocking on gaps in the list - `getSpotValue()`/`setSpotValue()` in `supabase-food.js` handle reading/writing through that fallback transparently, including for older `food_reviews` rows whose `spot` text doesn't match any curated name. No schema change - `food_reviews.spot` still just stores plain text, same as before this existed.
- **supabase-waittimes.js** — `RIDES_BY_PARK` (curated per-park attraction rosters, park names must match the ones used elsewhere) is now only the **offline fallback**: `updateRideOptions` is async and builds the ride list from the live feed instead, because the curated roster had measurably drifted (only 84 of its 101 names still matched, and `DINOSAUR`, `It's Tough to Be a Bug!` and `TriceraTop Spin` are gone from Animal Kingdom entirely). Picking a ride pre-fills Posted Wait via `handleRideSelect`, marked and fully editable - the sign in front of the ride is still the source of truth, and Actual Wait is never guessed at since that is the number this page exists to collect; `submitWaitTime`/`deleteWaitTime`; `renderWaitTimes` dispatches to `renderWaitTimesToday` (today's individual submissions, no averaging - live feed) and `renderWaitTimesYesterday` (per-ride average posted/actual wait, computed from yesterday's rows only); `switchWaitTimesTab`. "Today"/"yesterday" are just a filter on `created_at` against the viewer's local calendar day (`isSameLocalDay`) - nothing is ever archived or deleted, so a longer history is just a filter change away later.
- **waittimes-live.js** — live posted wait times from **themeparks.wiki**, powering the Wait Times page's "Live Now" tab and the log form's auto-filled Posted Wait. **This file is the entire third-party dependency**: if that service ever goes away, delete this file and the Live tab markup and the user-submitted wait times carry on untouched. Disney publishes no public API (their app talks to an internal authenticated endpoint), so an aggregator is the only option. No key and no signup, and it sends `access-control-allow-origin: *`, which is why this needs **no serverless function** despite every other outbound call in this project needing one. `TP_PARK_IDS` maps the app's exact park name strings to the feed's UUIDs; `tpFetchPark(park, force)` caches per park for five minutes (their stated refresh cadence, so polling faster spends requests without gaining freshness) and returns **null** rather than throwing.
  - **The rule that matters: this must never be folded into `loadData()`.** That function is one `Promise.all` over every table, so a single rejection takes down the whole app's data - the same gotcha the festivals migration had. This is a third-party endpoint that *will* fail eventually, so it stays isolated, every caller handles a null, and `renderWaitTimes` calls it without awaiting it. Verified by stubbing the fetch to throw: Live shows a retry message while Today, Yesterday and the rest of the app render normally.
  - **The attraction filter has two clauses and both are load-bearing.** The feed classes galleries, trails and walkthroughs as `ATTRACTION` (Mexico Folk Art Gallery, Discovery Island Trails); they are `OPERATING` with no queue, so they are dropped. But anything *not* operating is kept regardless, because a ride being down or refurbished is exactly what you want to know, and because **once a park closes for the night nothing has a wait at all** - filtering purely on "has a wait" made the board go blank at 22:00 and read as broken rather than as closed. Caught that during verification, not by reasoning. A park with no waits at all also gets an explicit "this park looks closed for the day" note.
  - **Disney publishes no wait times for Blizzard Beach or Typhoon Lagoon**, only open/closed (verified: zero standby entries, but real statuses, including a slide in refurbishment). Those two are in `TP_NO_WAITS` and render as a status-only list with a note saying so. **Volcano Bay does publish waits** and behaves normally, so do not lump the three water parks together.
  - Rows reuse `.lb2-row` for its padding and rules but take the pointer cursor back off, since a live row is not clickable. Open rides sort first by longest wait; closed ones sink to the bottom rather than being hidden.
- **supabase-donors.js** — Thank You page (`view-thanks`/`nav-thanks`, public, guest-browsable like Community/Food/Photos/Wait Times/About). `renderThanks()` builds the donor wall (`#donor-wall`) from `STATE.donors`; `donorChipHtml()` renders a linked chip (avatar + `@username`, click -> `openUserProfile`) for an entry with a live `user_id`, or a plain-text chip for one without. Does NOT re-override `loadData` — `STATE.donors` is populated in `supabase-food.js`'s fetch per the convention above. Admin-only "Add a Donor" panel (`#donor-admin-panel`, shown only when `STATE.currentUser.isAdmin`) toggles between picking a registered account (`switchDonorMode`/`donorUserSearch`/`donorPickEl`, same search-and-pick pattern as food items) and typing a plain display name for a non-account donor; `submitDonor()`/`deleteDonor()` insert/delete via RLS that only allows rows where `profiles.is_admin` is true for `auth.uid()` — enforced server-side, the client-side admin check is just UI convenience.
- **supabase-invite.js** — "Invite a Friend" in the profile dropdown (`openInvite`/`submitInvite`/`copyInviteLink`). Front end only collects the address and the optional note; the send happens in `api/invite.js`, because the Resend key has to stay on the server. It passes the caller's Supabase **access token** (`sb.auth.getSession()`) in an `Authorization: Bearer` header so the endpoint can prove who is asking rather than trusting a user id in the body. Errors come back from the endpoint and are shown in the modal rather than as a toast, so the address stays on screen to correct. Does NOT touch `loadData` — nothing about invites needs to be in `STATE`. The "or share the link yourself" copy field is a fallback for anyone who would rather paste the link into a text message; `navigator.clipboard` throws on insecure origins and in some mobile browsers, so it falls back to selecting the field.
- **leaderboard.js** — `buildLeaderboard` override + `LB_GROUPS` (Disney/Universal); `selectResort`/`selectLbPark`; two-level filter (resort -> park). Water parks folded in: Blizzard Beach + Typhoon Lagoon -> Disney; Volcano Bay -> Universal.
- **api/notify-signup.js** — **live and confirmed working end-to-end** (tested with a real throwaway signup, email landed in `help@goturnstiles.com`). The site's first (and so far only) serverless function, not a static file - Vercel auto-detects anything under `api/` as a Node function, no build config needed. Sends Sean an email through Resend every time someone signs up. Not called by the front end at all - it's called by a **Supabase Database Webhook** (found under **Database -> Integrations** in this project's dashboard, not directly under "Database" - the feature's internal name is "Hooks", URL path `/database/hooks`, labeled differently in different places) on `profiles` INSERT, since `handle_new_user()` inserts exactly one profile row per real new signup. Protected by a shared-secret header (`x-webhook-secret`) since the endpoint URL itself is public like any Vercel route. See its own top-of-file comment for the three required Vercel environment variables (`RESEND_API_KEY`, `NOTIFY_EMAIL` - set to `help@goturnstiles.com`, `SIGNUP_WEBHOOK_SECRET`) and exactly what to configure in each dashboard - none of that setup can be done from this repo, it's dashboard-only on both the Vercel and Supabase side. **Two real gotchas hit while setting this up, worth knowing if this ever needs touching again**: (1) this Supabase project didn't have the `pg_net` extension enabled, which threw `ERROR: 3F000: schema "supabase_functions" does not exist` when first creating the webhook - enabling `pg_net` under Database -> Extensions fixed it, this is what provisions the internal trigger machinery Database Webhooks depend on; (2) Vercel does **not** retroactively apply newly-added/changed environment variables to an already-live deployment - adding the three env vars above only takes effect after a fresh Redeploy (Deployments -> the deployment -> ⋯ -> Redeploy), which is why the very first real test came back `401` even though everything was configured correctly by that point.
- **api/invite.js** — the second serverless function, sending the "Invite a Friend" email through the same Resend account `notify-signup.js` already uses. **The only environment variable it needs is `RESEND_API_KEY`, which already exists** — `SUPABASE_URL`/`SUPABASE_ANON_KEY` fall back to the same public values shipped in `main.js`, so there is nothing new to configure in Vercel. Unlike `notify-signup.js` this one is called by the front end, which makes it a **public endpoint that sends mail**, i.e. an obvious spam relay if left open. Three things close it, and none of them should be removed casually: (1) the caller's access token is verified against `/auth/v1/user` at Supabase rather than trusted from the request body; (2) one validated recipient per request, and you cannot invite yourself; (3) every send is logged to `public.invites` and capped at **10 per user per rolling 24h**. The cap is enforced by reading that table back, so **if the table is missing the request is refused rather than allowed through uncounted** — fail closed, deliberately. The log row is written *before* the Resend call, so a failed send still counts against the cap; that is the safe direction to be wrong in. It reads and writes `invites` **as the caller, with their own token**, so RLS is what scopes it to their rows — no service_role key is involved anywhere. `fromName` has control characters stripped before it reaches the Subject header (a newline in a header value is the classic injection trick), and both it and the note are HTML-escaped into the email body since they are attacker-controlled text landing in HTML.

## Supabase
- Tables: `profiles` (has `avatar_url`, `disney_pass`/`universal_pass`, `is_admin`), `checkins`, `food_reviews` (has `spot`, `photo_url`), `photos`, `food_favorites`, `wait_times` (has `ride_id`), `donors`, `festivals`, `festival_reviews`, `festival_favorites`, `invites`. See `supabase/schema.sql`.
- Trigger `on_auth_user_created` auto-creates a profile from signup metadata.
- RLS: public read on everything **except `food_favorites`/`festival_favorites`, which are private (own rows only)** — they're personal reminder lists, not social content; write/update/delete only your own rows everywhere. **Exceptions**: `donors` is public-read but admin-only write — insert/delete require `profiles.is_admin = true` for the calling user, checked in the policy itself (not just client-side); `is_admin` is a manually-set flag, not a real role system — see the Thank You entry below for how to make an account admin. `festivals` is public-read with **no write policy at all** — new festivals are only ever added by hand via a direct SQL insert (see the EPCOT Festivals entry below), there's no in-app way to create one.
- The publishable key in main.js is SAFE (public by design; RLS protects data). NEVER commit the service_role key or DB password.
- Email confirmation is ON. Site URL still needs fixing — see "Custom domain is live" above.
- **Custom SMTP is set up via Resend** (Authentication -> Settings -> SMTP Settings), replacing Supabase's rate-limited default mailer. Domain `goturnstiles.com` verified in Resend via DNS records at Namecheap (DKIM TXT on `resend._domainkey`, SPF TXT on `send` — the accompanying SES bounce-handling MX record was skipped since Namecheap won't allow adding MX records while Mail Settings is on "Email Forwarding," and it's not required for mail to send/authenticate correctly, just for bounce routing completeness). Sender is `noreply@goturnstiles.com` or similar (doesn't need to be a real inbox — it's send-only). **Confirm signup** and **Reset Password** templates are re-styled (Authentication -> Email Templates) to match the site's navy/parchment/coral look, using `<table>` + `bgcolor` attributes and a `color-scheme` meta tag rather than plain CSS `background-color` — Gmail's mobile app was auto-dark-mode-remapping the original colors (navy → olive/brown) without that.

## Conventions / gotchas
- After editing any .js/.css, bump its `?v=N` in index.html or the browser serves stale.
- Photos: new uploads are downscaled client-side then pushed to the `photos` Storage bucket via `uploadPhoto()`; `photos.image_url` stores the public Storage URL. Older rows created before this change still have base64 data URLs in `image_url` — both render identically via `<img src>`, no backfill needed.
- STATE is a client cache; call `loadData()` after any write to refresh + rerender.
- Multi-line edits to index.html/*.js were done via a small Python script (io.open read/replace/write) run through Bash — reliable for multi-line HTML.
